## 3. 핵심 아키텍처 결정 및 판단 근거

### 3-1. 대전 기록 탭 설계 근거
- **판별 챔피언 정보의 가용성**: 조사 결과 모든 판에 6명의 챔피언 정보가 이미 100% 들어있으므로, 별도의 챔피언 데이터 보강 없이 즉시 대전 기록 탭에 챔피언 초상화와 이름을 노출할 수 있다.
- **기존 필터 체계와의 일관성**:
  - `index.html`은 이미 `pickGames()` 함수를 통해 `#period` 셀렉트 값(전체, 시즌 1, 시즌 2, 각 세션)에 따라 배열을 필터링하고 있다.
  - 새 탭(`history`)도 `pickGames()`가 반환한 `games` 배열을 그대로 입력받아 렌더링하면 기간 필터가 별도 비용 없이 자연스럽게 연동된다.
  - 플레이어 필터는 `#chips`의 `state.sel`에 선택된 인원이 있을 때 해당 인원이 `g.team1` 또는 `g.team2`에 포함된 판만 남기는 방식으로 구현할 수 있다.
- **모바일 UX 배려**:
  - 480px 이하에서 기존 5개 탭은 `grid-template-columns: repeat(5, minmax(0, 1fr))`로 꽉 차 있다. 탭이 6개로 늘어나면 라벨이 축약되거나 깨질 수 있으므로 가로 스크롤 방식(`overflow-x: auto`)을 적용하는 것이 안전하다.
  - 대전 기록 표는 좌우 정보량이 많으므로(선수 6명 + 챔피언 6개 + 라운드 + 일시), 모바일에서는 개인 탭의 `.player-mobile`처럼 카드형 리스트로 전환하여 세로로 편안하게 읽을 수 있도록 한다.

### 3-2. 즉시 반영 경로 및 갱신 방식 근거
- **현재 과도기**:
  - `game_recorder.py`가 GitHub API로 커밋하고 Cloudflare Pages가 빌드하는 방식은 약 30~90초의 불가피한 배포 지연이 발생한다.
  - 이 시기에는 열린 화면이 자동으로 알아채기 어려우므로, `visibilitychange` 이벤트(사용자가 롤 게임 후 브라우저로 돌아왔을 때)와 15초 주기 가벼운 HEAD 요청으로 새 JSON 배포를 감지하여 갱신하는 것이 가장 경제적이다.
- **향후 맥미니 직접 서빙 시기**:
  - `activity-integration/plan.md`에 따르면 맥미니의 정적 웹 서버(127.0.0.1:8791)가 봇의 로컬 `history_data.json`을 `Cache-Control: no-cache`로 직접 서빙한다.
  - 봇이 디스크에 `os.replace`로 원자적 쓰기를 마치는 순간(수 밀리초 이내) 즉시 최신 데이터가 외부에 노출된다.
  - 액티비티 화면은 봇의 WebSocket 연결을 통해 판 종료 즉시 푸시 알림을 받을 수 있고, 일반 웹 화면은 탭 활성화 시 즉각 최신 상태를 읽을 수 있다.

### 3-3. 재파싱 위험성과 안전 설계 근거
- **기존 `parse_all_history.py`의 치명적 결함**:
  - 코드에 명시되어 있듯이 `season`, `round_orig`, `current_season` 필드를 생성하지 않는다.
  - 이 스크립트를 실수로 실행하면 2026-07-14에 진행했던 시즌 1 연번 재부여(1~150)와 시즌 태그가 모두 지워져 마스터 데이터가 파괴된다.
  - 게다가 디스코드 embed에는 `/번복` 실행 사실이 반영되어 있지 않으므로 번복 데이터가 소실된다.
- **안전 재파싱 도구(`parse_history_v2.py`) 분리 원칙**:
  - 기존 파일을 절대 직접 덮어쓰지 않고 `history_data_reparsed.json`으로 출력한다.
  - 시즌 태깅 로직(2026-06-26 기준)과 원본 라운드 보존 로직을 스크립트 안에 하드코딩한다.
  - 기존 마스터 파일의 `corrected` 필드를 읽어 정합성을 유지하도록 병합 알고리즘을 둔다.
  - 디스코드 API 연속 호출에 따른 429(Rate Limit)를 방지하기 위해 비동기 딜레이를 부여한다.
- **재파싱의 의의와 한계**:
  - 현재 데이터는 시즌 1(150판)과 시즌 2(86판) 모두 구멍 없이 완벽한 상태이다.
  - 재파싱은 혹시라도 봇이 모르는 사이에 누락되었거나 건너뛴 라운드가 있었는지를 교차 검증하는 용도로 실행되어야 하며, 기존 데이터의 정합성을 훼손하는 수단이 되어서는 안 된다.
