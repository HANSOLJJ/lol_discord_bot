# 투기장 대전 기록 탭 추가 및 과거 전적 재파싱 계획

작성일은 2026-09-28이다. 이 문서는 롤 투기장 전적 사이트(arena.hansoljj.com)에 판별 상세 결과를 보여주는 '대전 기록' 탭을 추가하고, 과거 디스코드 기록을 안전하게 재파싱하여 데이터를 최신화 및 정합화하기 위한 상세 계획서이다.
진행 상황은 [checklist.md](checklist.md), 검토 근거와 파일 분석 수치는 [context-notes.md](context-notes.md)에 기록한다.

---

## 1. 배경과 목표

롤 투기장 봇은 6명의 플레이어가 3:3으로 나뉘어 게임을 진행하고 매 판 기록을 남긴다.
현재 전적 대시보드(arena.hansoljj.com)에는 개인, 2인 시너지, 3인 시너지, 챔피언, 3:3 매치업 통계가 제공되지만, 각 판마다 어떤 팀이 어떤 선수와 챔피언으로 대결하여 누가 이겼는지를 보여주는 '대전 기록' 목록이 없다.

향후 봇은 운영 개선에 따라 TEAM1·TEAM2 음성 채널 채팅에는 일체 메시지를 보내지 않고, 팀짜기 채널과 디스코드 액티비티(Discord Activity)만을 사용하도록 전환될 예정이다. 이에 따라 게임 결과는 arena 대시보드에 지연 없이 즉시 반영되어야 한다.
또한 음성 채널 채팅 기록이 더 이상 생성되지 않기 전에, 과거 디스코드 3개 채널에 흩어져 있는 전적 embed를 최종적으로 재파싱하여 누락 없는 가장 정확한 전적 데이터를 확보하고자 한다.

본 계획의 목표는 다음과 같다.
1. 대전 기록 탭을 대시보드에 추가하여 판별 라운드, 일시, 양 팀 선수 및 챔피언 초상화, 승리 팀, 번복 여부를 직관적으로 제공한다.
2. 현재(GitHub Contents API + Cloudflare Pages)와 향후(맥미니 로컬 정적 웹 서버 서빙) 두 시기의 즉시 반영 경로를 정의하고 열린 화면의 자동 갱신 방안을 마련한다.
3. 운영 데이터를 파괴하지 않는 안전한 재파싱 절차, 검증 기준, 백업 및 롤백 절차를 확립한다.

## 3. 상세 설계안

### 3-1. 대전 기록 탭 설계 (`index.html`)

#### 1) 탭 네비게이션 확장
- 탭 키: `history`, 라벨: `대전 기록`.
- 기존 5개 탭에 이어 6번째 탭으로 추가한다.
- 480px 이하 모바일 화면 대응: 기존 `grid-template-columns: repeat(5, minmax(0, 1fr))`는 6개 탭이 되면 글자가 잘릴 위험이 있다. 가로 스크롤 탭 바(`overflow-x: auto; flex-wrap: nowrap`) 또는 2행 그리드로 조정하여 모바일 가독성을 확보한다.

#### 2) 판 목록 카드 및 테이블 구조
- 기본 정렬: 최신 판이 가장 위에 오도록 역순(내림차순, R86 → R85 → ...)으로 배치한다.
- 각 판 표시 항목은 다음과 같다.
  - 헤더 영역: 라운드 번호(`시즌 {season} R{round}`), 경기 시각(예: `2026-09-26 18:31` 또는 오늘/어제 등 상대 시각), 승리 팀 배지(초록색 `TEAM 1 승리` 또는 `TEAM 2 승리`).
  - 본문 영역: 양 팀 대진 배치 (좌: TEAM 1, 우: TEAM 2).
    - 각 팀당 3명의 선수 이름 및 플레이한 챔피언 초상화.
    - Data Dragon 초상화(`portrait(champ, 'sm')`)와 텍스트 대체재(`champ-fallback`)를 함께 제공한다.
    - 승리한 팀 영역은 배경 하이라이트(승리 테두리/배경색)를 주고, 패배한 팀은 투명도를 낮추어 승패를 직관적으로 식별할 수 있게 한다.
  - 메타데이터 영역은 다음과 같다.
    - 번복(`corrected`) 표시: `game.corrected` 필드가 존재하는 경우, 주황색/경고 배지로 `번복됨 (이전 승자: {from}, {at} 정정)`을 눈에 띄게 노출한다.
    - 데이터 출처 배지: `BOT`, `3채널 교차`, `팀짜기 단독` 등의 소스 태그를 보조 정보로 표시한다.

#### 3) 필터 연동
- 기간 필터 연동: 상단 `#period` 셀렉트(전체, 시즌 1, 시즌 2, 세션 S01~S13) 변경 시 `pickGames()` 결과가 즉시 대전 기록 탭 목록에 반영된다.
- 인원 칩 연동: `#chips`에서 특정 플레이어를 클릭하여 선택하면, 해당 플레이어가 출전한 경기만 목록에 필터링된다.
- 챔피언 필터 추가: 대전 기록 탭 상단에 챔피언 선택 드롭다운 또는 입력 필터를 두어 특정 챔피언이 등장한 판만 빠르게 조회할 수 있게 한다.

#### 4) 모바일 전용 뷰
- 768px 이하 및 480px 이하에서는 테이블 대신 반응형 카드 레이아웃으로 전환한다.
- 터치 인터랙션을 고려하여 카드 패딩과 글자 크기를 확보하고, 챔피언 초상화 터치 시 기존 `champ-info` 팝업을 연계하여 챔피언 전적을 확인할 수 있게 한다.

### 3-2. 즉시 반영 경로 및 실시간 갱신 설계

`.agents/plans/activity-integration/plan.md`의 아키텍처에 맞추어 전환 전(현재)과 전환 후(향후) 두 시기의 반영 경로를 정의한다.

#### 1) 시기별 반영 경로 및 지연 비교

| 구분 | 1단계: 현재 (과도기) | 2단계: 향후 (통합 완료 후) |
|---|---|---|
| 결과 확정 진입점 | `/승리` Discord 슬래시 명령 | 액티비티 결과 입력 또는 `/승리` 명령 |
| 로컬 마스터 저장 | 맥미니 로컬 `data/history_data.json` 원자적 저장 | 맥미니 로컬 `data/history_data.json` 원자적 저장 |
| 외부 공개 경로 | GitHub Contents API 커밋 → Cloudflare Pages 배포 | 맥미니 정적 웹 서버(127.0.0.1:8791) 직접 서빙 |
| DNS / 터널 | Cloudflare Pages 기본 도메인 | Cloudflare Tunnel (`arena.hansoljj.com`) |
| 예상 반영 지연 | **약 30초 ~ 90초** (GitHub API 2초 + Pages 빌드 30~60초) | **0.1초 미만** (디스크 원자적 교체 즉시 반영) |
| 백업 방식 | GitHub Pages 배포가 백업을 겸함 | GitHub 커밋은 백그라운드 오프사이트 백업으로 유지 |

#### 2) 열린 화면의 새 결과 갱신 방법

- **문제점**: 현재 `index.html`은 최초 로드 시 1회만 `fetch("history_data.json?t=" + Date.now())`를 호출한다. 페이지를 띄워둔 상태에서는 새 경기가 끝나도 자동으로 화면이 갱신되지 않는다.
- **해결 방안**:
  1. **디스코드 액티비티 화면**:
     - 봇 프로세스 내 aiohttp 서버가 게임 완료 시 WebSocket으로 연결된 모든 액티비티 클라이언트에 상태 갱신 이벤트(`state` 또는 `history_updated`)를 브로드캐스트한다.
     - 액티비티 클라이언트는 이벤트를 받자마자 내부 상태를 갱신하거나 `history_data.json`을 다시 읽는다.
  2. **일반 브라우저 웹 화면 (`arena.hansoljj.com`)**:
     - **포커스 감지 자동 재조회 (`visibilitychange`)**: 게임을 하고 브라우저 탭으로 돌아왔을 때 사용자가 F5를 누르지 않아도 즉시 최신 데이터를 확인하도록 `document.visibilityState === "visible"` 시 헤더 확인 또는 재fetch를 수행한다.
     - **경량 폴링 (Polling)**: 화면이 켜져 있는 동안 15~20초 주기로 `HEAD history_data.json`을 요청하여 `ETag` 또는 `Last-Modified`가 변경되었을 때만 전체 JSON을 다시 가져온다. 맥미니 정적 웹 서버 환경에서는 `Cache-Control: no-cache`가 적용되므로 항상 최신 헤더가 반환된다.
     - **수동 새로고침 UI**: 대시보드 상단에 마지막 갱신 시각과 "새로고침" 아이콘 버튼을 배치하여 사용자가 원할 때 언제든 즉시 데이터를 재호출할 수 있도록 한다.

### 3-3. 과거 전적 안전 재파싱 계획

#### 1) 재파싱의 목적과 배경
현재 기록된 236판 중 시즌 2의 R33~R86은 `game_recorder.py`를 통해 디스코드 API와 분리되어 봇이 파일에 직접 기록한 데이터이다.
향후 봇이 TEAM1·TEAM2 음성 채널 메시지 전송을 중단하면, 과거처럼 3개 채널에 걸쳐 전송된 결과 embed를 교차 검증할 수 있는 기회는 이번이 마지막이 된다.
혹시 모를 누락된 판이나 라운드 건너뜀이 있었는지 검증하기 위해 디스코드 전체 히스토리를 재스캔하되, 기존 마스터 데이터를 절대로 손상시키지 않는 방식으로 진행해야 한다.

#### 2) 안전한 재파싱 도구 설계 (`parse_history_v2.py`)
기존 `parse_all_history.py`의 결함을 보완한 전용 재파싱 도구를 구상한다.
- **기존 파일 직접 덮어쓰기 금지**: 출력 대상 경로를 `data/history_data_reparsed.json`으로 격리한다.
- **메타데이터 복원 규칙 내장**:
  - `season`: 2026-06-26 이전 경기는 시즌 1, 이후 경기는 시즌 2로 태깅한다.
  - `round_orig`: 디스코드 embed에 적혀 있던 원래 라운드 번호를 보존한다.
  - 시즌 1 라운드 연번: 시즌 1(150판)은 시간순으로 1~150의 연속 번호를 부여한다.
  - 최상위 메타데이터: `current_season: 2`를 명시적으로 유지한다.
- **기존 번복(`corrected`) 및 플레이어 이름 보존**:
  - 기존 마스터 파일(`history_data.json`)을 읽어, 매칭되는 판에 `corrected` 기록이 있다면 새 파싱 결과에 그대로 이식한다.
  - 플레이어 ID별 이름 매핑도 기존 매핑을 우선 보존한다.

#### 3) 검증 기준 (성공 판정 체크리스트)
재파싱 결과를 마스터 데이터로 채택하기 위해 다음 기준을 100% 만족해야 한다.
1. **총 판수 검증**: 총 판수가 최소 236판 이상이어야 한다. 만약 판수가 236판보다 적다면 채널 스캔 누락이 발생한 것이므로 즉시 폐기한다. 만약 236판보다 많다면, 어떤 판이 추가로 발견되었는지 시간대와 내용을 정밀 대조한다.
2. **시즌별 판수 검증**:
   - 시즌 1: 정확히 150판이어야 한다 (PARSE_REPORT에 따라 검증된 진실).
   - 시즌 2: 최소 86판 이상이어야 한다.
3. **개인 승수 및 wins.json 대조**:
   - 시즌 1: 6인의 총 승수 합이 450 (150 × 3)이어야 한다.
   - 시즌 2: `wins.json`의 각 플레이어 승수 및 `total_rounds`와 재파싱 데이터의 판별 승자 합계가 1인당 1승의 오차도 없이 완전히 일치해야 한다.
4. **챔피언 정보 결측치 검증**: 모든 판의 모든 참가자(판당 6명)에 챔피언 문자열이 채워져 있어야 한다 (결측치 0%).
5. **라운드 연속성 검증**: 시즌 1(1~150)과 시즌 2(1~현재)의 라운드 번호에 중복이나 빈 구멍이 없어야 한다.

#### 4) 위험 요인 및 완화 대책
- **위험 1: 디스코드 API Rate Limit 및 계정 차단**
  - 원인: 3개 채널의 수만 개 메시지 히스토리를 `limit=None`으로 연속 호출 시 디스코드 API 429(Too Many Requests) 또는 비정상 트래픽 감지 위험이 있다.
  - 대책: 메시지 배치마다 비동기 슬립(예: 100개당 0.2초)을 두고, 지수 백오프(Exponential Backoff)를 적용한다. 운영 봇이 유휴 상태인 야간에 실행한다.
- **위험 2: 운영 마스터 데이터 오염**
  - 원인: 파서 실행 실수로 빈 파일이 저장되거나 시즌 태그가 날아간 구형 스키마로 덮어써질 위험이 있다.
  - 대책: 파서는 무조건 별도 파일(`history_data_reparsed.json`)로만 저장하며, 승인된 비교 검증 스크립트 통과 전까지는 원본 파일을 교체하지 않는다.
- **위험 3: 번복 기록 유실**
  - 원인: 디스코드 embed에는 `/번복` 실행 사실이 남지 않고 이전 승리 embed만 남아있을 수 있다.
  - 대책: 기존 파일의 `corrected` 필드를 최우선 정답으로 취급하여 새 파싱본에 병합한다.

#### 5) 백업 및 롤백 절차
1. **사전 백업**:
   - 실행 전 현재 파일들을 타임스탬프와 함께 보관한다.
   - `cp history_data.json history_data.json.bak_$(date +%Y%m%d_%H%M%S)`
   - `cp wins.json wins.json.bak_$(date +%Y%m%d_%H%M%S)`

   - Git 브랜치 상태를 확인하여 커밋되지 않은 임시 파일을 정리한다.
