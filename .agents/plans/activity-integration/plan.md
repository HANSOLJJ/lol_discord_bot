# 롤 봇·액티비티·전적 통합 실행 계획

작성일은 2026-09-28이다. 이 파일을 액티비티 구현과 두 저장소 기능 통합의 기준 문서로 사용한다.
진행 상태는 [checklist.md](checklist.md), 결정 이유와 검토 근거는 [context-notes.md](context-notes.md)에 기록한다.
이번 작업은 문서 통합이며, 아래 구현·운영 전환·Git 병합은 아직 수행하지 않았다.

## 1. 목표와 범위

첫 성공 기준은 **TEAM1·TEAM2에서 카운트다운이 안정적으로 보이고, 연결 문제를 알 수 있으며, 재접속과 모바일 복귀 후 현재 게임으로 돌아오는 것**이다.
최종 목표는 `lol_discord_bot`과 `lol_arena`를 하나의 Git 저장소에서 관리하고 게임 처리와 전적 데이터를 함께 사용하는 것이다.

| 단계 | 사용자 경험 | 범위 |
|---|---|---|
| 1차 | `/게임시작` → 액티비티에서 픽 → 기존 `/승리` → 기존 전적 조회 | 카운트다운과 픽 안정화가 우선이다. 기존 결과 기록 경로를 유지한다. |
| 통합 목표 | 게임 시작 → 픽 → 결과 대기 → 결과 입력 → 오늘 전적·누적 통계 | 액티비티와 Discord 명령이 같은 서버 함수를 호출한다. 일반 웹 전적 조회도 유지한다. |

한 액티비티에서 결과 입력과 통계까지 연결하는 것은 통합 목표안이다. 결과 입력 권한, 시즌 관리·번복 UI의 포함 범위는 해당 단계 착수 전에 결정한다.
고정 6명·챔피언 후보 8개·활성 게임 1개로 시작한다. 다중 길드 동시 게임이나 새 프레임워크 도입은 이번 계획에 포함하지 않는다.

## 2. 유지하는 결정과 수정한 설계

| 항목 | 실행 방향 |
|---|---|
| 픽 화면 | Discord Activity, Embedded App SDK를 사용한다. |
| 게임 서버 | 기존 Python 봇 프로세스에 aiohttp HTTP·WebSocket 서버를 추가한다. 상태와 `pick_lock`은 한 프로세스가 소유한다. |
| 실행 위치 | 맥미니, `127.0.0.1:8790` 바인딩, 기존 `finance` Cloudflare Tunnel을 활용한다. |
| 공개 주소 | 웹은 `arena.hansoljj.com`, API는 `pick.hansoljj.com`을 사용한다. |
| 프론트 | Vite + `@discord/embedded-app-sdk`, 바닐라 JS로 시작한다. |
| 채널 메시지 | 팀 구성·픽 현황판과 액티비티 실행 버튼을 유지한다. 액티비티 모드에서는 매초 메시지를 편집하지 않는다. |
| 전환 | `pick_ui: embed / activity`를 판 시작 시 고정한다. 한 판 중간에 두 타이머를 혼용하지 않는다. |
| 개발 | `롤랜덤챔프봇-dev` 앱과 TEST2를 사용하고 운영 토큰·전적과 분리한다. |
| 자동 기동 | pm2에 봇을 등록하고 launchd를 통한 복귀를 검증한다. |
| 시계 | 보정된 서버 시각을 기준으로 `performance.now()` 경과 시간을 더해 그린다. 모바일 복귀 시 재동기화한다. |
| 저장소·배포 | 하나의 저장소를 목표로 하되, Pages에는 웹 빌드 결과만 배포한다. 기존 저장소 루트 전체 서빙은 통합 후 사용하지 않는다. |

기존 설계의 `Date.now() + offset` 반복 계산, 재클릭 취소 보장, `gather`만으로 느린 소켓 해결, 재인증만으로 게임 복구된다는 가정은 아래 내용으로 대체한다.

## 3. 현재 문제와 확인된 근거

- 메시지 편집은 봇 → Discord API → 사용자 앱을 거친다. 매 숫자가 이 경로에 의존한다.
- `got_champe.py`의 초기 메시지 전송은 성공한 채널만 `champion_messages`에 등록한다. 일부 채널 전송이 실패해도 다른 채널에서 성공하면 게임을 시작한다. 실패 채널의 메시지를 다시 만드는 처리는 없다.
- `push_channel_embed`는 편집 예외를 `except Exception: pass`로 무시한다. 특정 채널이 계속 갱신되지 않아도 원인 로그가 남지 않는다.
- 편집이 밀린 채널에는 중간 상태를 건너뛰고 최신 상태만 보낸다. 숫자가 빠질 수 있다.
- 사용자가 특정 채널에서 카운트다운 자체가 보이지 않았다고 보고했다. 위 경로는 가능한 원인이며 당시 사건의 원인은 로그 없이 확정할 수 없다.
- 기존 횟수 기반 1.2초 박자에서는 표시 20초가 실제 약 24초 이상이 될 수 있다. 액티비티는 실제 경과 시간 20초를 기준으로 한다. 사용자가 체감하는 선택 시간이 달라짐을 운영 전환 때 확인한다.

과거 V1~V3 분석은 [COUNTDOWN_ANALYSIS.md](../../../docs/COUNTDOWN_ANALYSIS.md)에 보존한다. 그 문서의 당시 해결 결론은 현재 안정성을 보장하지 않는다.

## 4. 전체 구조와 게임 연결

```text
Discord Activity (TEAM1 / TEAM2, PC / 모바일)
  /pick-api/* → Discord 프록시 → pick.hansoljj.com → finance 터널
                                                     → 127.0.0.1:8790
                                                       봇 + aiohttp
                                                       공통 게임·결과 처리
  /ddragon/* → Discord 프록시 → Data Dragon
  /          → Discord 프록시 → arena.hansoljj.com/pick/

Discord 명령 ────────────────→ 같은 게임·결과 처리
일반 웹 전적 화면 ───────────→ 전적 조회 (통합 단계)
```

### 4-1. 같은 게임으로 연결하기

- 서버가 재사용되지 않는 `game_id`를 생성한다. 재시작 시 0으로 돌아가는 메모리 카운터만 외부 식별자로 쓰지 않는다.
- 게임은 길드·허용 채널·참가자 6명에 연결한다. TEAM1과 TEAM2에서 각각 연 액티비티 인스턴스는 같은 서버 게임을 본다.
- `instance_id`는 Discord 액티비티 실행 인스턴스이며 게임 ID와 별도이다. SDK의 `guildId`, `channelId`, `instanceId`는 클라이언트 힌트이므로 서버에서 검증한다.
- OAuth 신원을 확인한 뒤 봇이 아는 길드·게임 참가 정보와 대조한다. 실제 액티비티 위치 검증에는 Activity Instance API를 사용한다. 인증 성공만으로 모든 게임 상태를 방송하지 않는다.
- 최초 연결·재접속 시 전체 스냅샷을 받는다. 활성 게임이 없으면 대기 화면을 보여준다.

### 4-2. 상태 흐름

`none → starting → picking → awaiting_result → completed`를 사용한다. 중단된 게임은 `aborted`로 표현한다.
1차에서도 픽 완료와 승리 기록 완료를 구분한다. 결과 입력 UI는 통합 단계에서 붙인다.
서버 재시작 시 진행 상태는 자동 복원되지 않는다. 기존 게임을 이어 하는 것처럼 표시하지 않고 중단·새 판 시작을 안내한다.
진행 상태 영속 복구가 필요하면 결과 저장 설계와 함께 별도 결정한다. 완료된 전적 보존과 진행 중 판 복구는 별개이다.

## 5. 카운트다운과 마감 판정

### 5-1. 서버가 정하는 시간

- 차례 시작에 `pick_timeout`과 `pick_grace_seconds`를 고정하고 마감을 미리 정한다. 액티비티 모드에서 카운트 중 `inf`를 쓰지 않는다.
- 서버 내부 경과 시간·마감 판정에는 단조 시계(`loop.time()` 또는 `time.monotonic()`)를 일관되게 사용한다. 외부 스냅샷은 유닉스 밀리초로 보낸다.
- 스냅샷의 `server_ms`와 `deadline_ms`는 같은 순간에 잡은 서버 시각·남은 시간으로 계산한다. 서버 시스템 시계가 보정되어도 내부 선택 시간이 늘거나 줄지 않게 한다.
- 타이머는 남은 시간 + 유예 동안 대기한 뒤 락 안에서 게임·턴·마감·미선택 상태를 재검증한다. 턴이 바뀌면 이전 타이머는 취소하고 식별자로도 방어한다.
- 자동 시작도 `start_at_ms`를 전달하고 서버 타이머가 전환한다. 클라이언트가 먼저 시작시키지 않는다.
- WS 요청은 핸들러가 메시지를 받은 직후, 락이나 다른 작업을 기다리기 전에 접수 시각을 기록한다. 클라이언트가 보낸 클릭 시각은 판정에 쓰지 않는다.
- 해당 턴이 아직 유효하고 `received_at <= deadline + grace`인 요청만 인정한다. 이미 자동 배정으로 끝난 턴을 늦은 요청으로 되돌리지 않는다. 경계 시점 경합을 테스트한다.
- 구 embed 모드의 Discord 스노플레이크 판정은 유지한다. 공통 함수에는 각 모드에서 정한 시각을 일관된 기준으로 전달하며 시계 단위를 혼용하지 않는다.

### 5-2. 클라이언트 시계 보정과 표시

1. 연결 후 5회의 ping/pong을 측정한다. 요청 ID로 응답을 대응시키고, 송수신 시각 `p0`, `p1`은 `performance.now()`로 잰다.
2. 서버가 pong 생성 시 넣은 유닉스 밀리초 `s`를 사용한다. RTT가 가장 작은 유효 샘플에서 수신 시각의 서버 시각을 `s + (p1 - p0) / 2`로 추정한다.
3. 다음 기준점을 저장하고 `requestAnimationFrame`에서 계산한다. 숫자가 변할 때만 DOM을 갱신한다.

```js
// 보정된 서버 시각에 단조 시계의 경과 시간을 더해 남은 시간을 계산한다.
const anchorServerMs = s + (p1 - p0) / 2;
const anchorPerfMs = p1;
const estimatedServerNow = anchorServerMs + (performance.now() - anchorPerfMs);
const remaining = Math.max(0, Math.ceil((deadlineMs - estimatedServerNow) / 1000));
```

4. 전경에서 30초마다 재측정한다. 재동기화 때 기준점과 현재 턴·마감 스냅샷을 함께 확인한다. 연결 세대가 바뀐 이전 응답은 버린다.
5. 최초 상태와 시간 동기화 전에는 `연결 중`을 표시한다. 임의의 20초를 먼저 시작하지 않는다.
6. 0이 되면 `마감 확인 중…`을 표시한다. 서버의 확정 응답 전까지 클라이언트가 자동 배정하거나 다음 턴으로 넘어가지 않는다.

이 방식은 사용자 PC의 `Date.now()` 변경에 영향을 덜 받는다. 네트워크 비대칭·서버 지연·프레임 지연이 있으므로 오차가 항상 0.15초 이내이거나 모든 기기에서 숫자가 완전히 같다고 보장하지 않는다.
`performance.now()`도 절전 중 경과 측정에 플랫폼 차이가 있으므로 아래 복귀 절차가 필수이다. 근거는 [MDN](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now)에 있다.

### 5-3. 연결 끊김과 모바일 복귀

- 연결이 끊겨도 현재 턴 정보를 이미 받은 전경 화면은 카운트다운을 계산할 수 있다. `연결 끊김`을 함께 표시하고 선택 버튼은 비활성화한다.
- 끊긴 동안 클릭을 저장했다가 다음 턴에 자동 전송하지 않는다. `전송 중`과 `선택 완료`를 구분하고 서버 응답 또는 스냅샷으로 확정한다.
- 0.5 → 1 → 2 → 5초 간격으로 재접속한다. 재연결 후 인증·전체 상태·시계 동기화가 끝나면 입력을 연다.
- `visibilitychange`로 전경 복귀하거나 연결이 다시 열리면 전체 상태와 ping 묶음을 다시 요청한다. 멈춰 있던 숫자를 순서대로 재생하지 않는다.
- 앱이 정지된 동안 화면이 계속 갱신된다고 보장하지 않는다. 복귀 시 최신 서버 상태로 즉시 따라가는 것이 검증 목표이다.
- 유예는 기존 2초를 초기값으로 유지하고 실제 지연 측정 후 조정한다. 0.2~0.3초 왕복을 가정해 미리 줄이지 않는다.

## 6. WebSocket 계약과 동시성

JSON 텍스트를 사용한다. 서버 시각은 유닉스 밀리초, Discord ID는 문자열이다. 6명·8후보 규모이므로 상태 변경마다 전체 스냅샷을 보낸다.

| 메시지 | 필수 정보 |
|---|---|
| `state` | `protocol_version`, `server_epoch`, `game_id`, `state_version`, `phase`, `round`, `season`, `server_ms`, `start_at_ms`, `deadline_ms`, `grace_ms`, `turn_id`, `current_index` |
| `state`의 화면 데이터 | `players`(id·이름·아바타·팀·승수), `pick_order`, `champions`(후보 ID·이름·이미지), `selections`, `auto_assigned`, 내 권한 |
| `ping` / `pong` | 요청 ID, 클라이언트가 보낸 값, 서버 pong 생성 시각 |
| `sync` | 요청 ID. 현재 권한으로 볼 수 있는 전체 `state`를 다시 요청한다. |
| `pick` | `request_id`, `game_id`, `turn_id`, `champion_id` |
| `reply` | `request_id`, `ok`, 기계 판독용 `code`, 표시용 `message`, 처리 후 `state_version` |

상태에 적용되지 않는 시간·턴 필드는 `null`로 정의한다. 게임 없음과 결과 대기에서도 의미가 모호한 예전 deadline을 유지하지 않는다.

- 서버는 락 안에서 세대·게임·턴·권한·후보 포함 여부·중복 선택·마감·요청 중복을 확인하고 상태를 변경한다.
- `(사용자, game_id, request_id)`별 처리 결과를 해당 게임 수명 동안 보존한다. 같은 요청 재전송에는 기존 결과를 반환하고, 같은 ID로 다른 내용을 보내면 거절한다.
- `state_version`은 게임 내 변경마다 증가한다. 서버 재시작은 `server_epoch`, 새 판은 `game_id`로 구분한다. 클라이언트는 현재 연결에서 더 오래된 버전의 스냅샷을 적용하지 않는다.
- 락 안에서는 스냅샷을 만들고 통신은 락 밖에서 한다. 소켓당 송신 작업 하나와 최신 스냅샷 병합으로 순서를 보장한다. 제한 시간을 넘긴 느린 연결은 닫고 재접속으로 복구한다.
- `gather`로 병렬 전송하는 것만으로 완료 대기와 전송 누적이 해결된다고 가정하지 않는다.
- 픽은 현재 동작에 맞춰 클릭 즉시 확정을 기본안으로 삼는다. 기존 코드의 취소 분기는 선택 직후 턴이 넘어가 정상 흐름에서 도달하지 않는다. 취소 기능이 필요하면 이전 턴 복귀·마감·다음 사람 선택의 관계부터 결정한다.

## 7. 인증과 권한

1. `discordSdk.ready()` 후 `commands.authorize`로 `identify` 범위의 OAuth code를 얻는다.
2. `POST /pick-api/token`으로 code를 보내고 서버가 client secret으로 교환한 뒤 `/users/@me`에서 신원을 확인한다.
3. 서버는 만료 시각이 있는 임의 세션을 발급한다. 클라이언트는 access token으로 SDK `authenticate`를 호출하고 세션으로 WS를 인증한다.
4. 서버는 신원과 4절의 게임 연결 정보를 대조해 참가·관전 권한을 부여한다. 참가자는 자기 차례에만 고를 수 있다.

OAuth HTTP는 aiohttp `ClientSession`을 재사용하며 이벤트 루프를 막지 않는다. 토큰·secret·인증 query를 로그에 남기지 않는다.
WS query로 세션을 전달하는 최소안은 짧은 수명과 로그 마스킹을 함께 적용한다. 세션 만료와 서버 재시작은 4401 종료 후 재인증한다.
`prompt: none`이 항상 성공한다고 가정하지 않는다. 동의가 필요하거나 실패하면 로그인 재시도 안내를 보여준다.
허용되지 않은 관전자는 게임 상태를 받지 않는다. 결과 입력·번복·시즌 변경 권한은 공통 서버 함수에서 검사하도록 통합 단계에 정의한다.
DEV_MODE의 가상 6명 조작도 TEST2의 허용된 테스트 사용자로 제한한다. 인증된 임의 사용자에게 턴 우회를 열지 않는다.
Cloudflare Access 로그인은 붙이지 않는다. 토큰 교환 경로는 공개 진입점이므로 요청 형식·크기·빈도를 제한한다.
`frame_id` 존재 여부는 화면 분기용이며 인증 근거가 아니다.

## 8. 봇 변경 경계

- 새 `activity_server.py`는 HTTP·세션·WS 연결을 맡고 `get_snapshot`, `on_pick` 등의 콜백을 주입받는다. 봇 전역 상태를 직접 import하지 않는다.
- `asyncio.run(main())`에서 웹 서버를 시작하고 `await bot.start(token)`을 실행한다. 재호출되는 `on_ready`에서 서버를 띄우지 않는다. 종료 시 소켓·HTTP 세션·runner와 타이머를 정리한다.
- `ChampionButton.callback`의 판단·변경을 공통 픽 함수로 추출한다. Discord 응답·버튼 색 갱신과 게임 규칙을 분리하고 구 모드 회귀 테스트부터 통과한다.
- activity 모드에서는 시작·턴 변경·픽·자동 배정·완료 때만 현황판을 갱신한다. `픽 화면 열기` 버튼 1개를 남기고 카운트다운 숫자는 넣지 않는다.
- `LAUNCH_ACTIVITY`는 응답 type 12이다. 기존 조사에서는 py-cord 2.8.1에 헬퍼가 없어 raw callback을 계획했다. 구현 시 설치 버전의 지원 여부를 확인하고 이중 응답하지 않는다.
- 초기 메시지·편집 실패에 채널 ID·게임 ID·에러 종류를 기록한다. 부분 실패를 사용자에게 알리고, 메시지가 없는 채널의 실행 진입 경로도 확인한다. 전송이 적어져도 실패가 사라진다고 보장하지 않는다.
- 1차는 `/승리`, `/번복`, `/시즌시작`, `game_recorder`의 기존 기록 경로를 유지한다. 결과 통합은 10절의 별도 단계이다.

## 9. 웹·저장소 통합과 배포

### 9-1. 저장소 정리

최종 저장소는 봇 코드, 웹 소스, 공통 계약 문서와 테스트를 함께 관리한다. 기존 봇 경로를 유지하고 `web/` 아래 액티비티와 전적 화면을 두는 구성을 최소 변경안으로 삼는다.
기준 원격 저장소·공개 범위·Git 이력 보존 방식은 실제 병합 전 결정한다. `.env`, 실데이터·백업·로그·가상환경을 새로 추적하지 않는다.
미커밋 변경과 봇의 데이터 자동 커밋을 먼저 확인하고, 원격 최신 상태를 읽어 병합 계획에 반영한다. 두 `.git`을 단순 삭제하거나 작업 파일을 덮어쓰지 않는다.

### 9-2. 개발 골격에서 통합 저장소까지

- 측정용 골격은 현재 두 저장소에서 시작할 수 있다. 임시 소스 위치는 `lol_arena/activity/`, 이전 설계의 빌드 출력은 `lol_arena/pick/`이다.
- dev 통신 검증 후 본격 UI 구현 전에 통합 위치를 확정한다. 통합 후 빌드 산출물은 예를 들어 `web/dist/`로 모으고 루트 전적 화면과 `/pick/` 경로를 함께 내보낸다.
- 기존 산출물 커밋 방식은 전환기 선택지이다. 최종 방식은 웹 소스·잠금 파일을 커밋하고 Pages 빌드의 출력 디렉터리만 게시하는 것을 기본안으로 한다.
- Pages의 저장소 연결·빌드 루트·명령·출력 경로를 함께 변경한다. 봇 실행 cwd·pm2·`paths.py` 상대경로·환경 파일 위치가 유지되는지 검증한다.
- 봇과 웹 배포는 각각 수행할 수 있다. `protocol_version` 불일치는 새로고침·업데이트 안내로 처리하고 오래 열린 웹앱과 새 서버의 조합을 검증한다.

### 9-3. 화면과 자산

모바일 세로를 기준으로 큰 카운트다운·현재 차례, 챔피언 8개, 팀별 픽순·승수·선택 현황, 서버 응답 토스트와 연결 상태를 배치한다.
선택 중 중복 입력을 막고 내 차례를 강조한다. 자동 배정은 별도로 표시한다.
Data Dragon 이미지는 `/ddragon/...`으로 요청한다. 전적 화면의 외부 폰트와 이미지도 액티비티 안에서 동작하도록 자산 경로를 확인한다.
기존 웹 전적의 개인·2인/3인 시너지·챔피언·매치업·시즌/세션 필터를 보존한다. 별도 통계 구현을 복제하지 않는다.
`base: ./`를 출발점으로 Discord의 `/`와 일반 웹 `/pick/`에서 자산 로딩을 검증한다. 일반 웹 `/pick/`은 Discord 실행 안내를, 전적 화면은 일반 조회 기능을 제공한다.

## 10. 결과 입력과 전적 통합

현재 흐름은 승수 파일 저장 → 별도 판 기록 저장 → GitHub Contents API로 JSON 배포 → 웹 최초 fetch이다.
승수 저장 후 판 기록 저장이 실패할 수 있고, GitHub 업로드 성공과 공개 웹 반영 완료도 서로 다르다.

1. 결과 입력 전에 저장 기준을 선택한다. `history_data`를 기준으로 승수를 계산·복구하거나 SQLite 트랜잭션으로 함께 저장하는 방식을 비교한다. DB 도입은 아직 확정하지 않았다.
2. Discord와 액티비티가 같은 `record_result` 계열 함수를 호출하도록 한다. 중복 결과 요청은 한 번만 기록하며, 중간 실패·재시작 후 재시도도 검증한다.
3. 기록의 식별자와 기존 `season`, `round`, `round_orig`, `current_season`, `corrected`, `sources`를 보존한다. 과거 라운드 번호를 새 게임 ID로 대체해 유실시키지 않는다.
4. 전적 조회 API를 제공하고 결과 확정·번복·시즌 변경 시 열린 화면이 다시 읽도록 알린다. 일반 웹과 액티비티의 주소·인증·CORS 동작을 각각 검증한다.
5. GitHub JSON 배포를 제거하기 전에 봇 중단 시 공개 전적을 읽을 방법을 결정한다. 읽기용 스냅샷을 남긴다면 갱신 시각을 표시하고 서버 원본과 구분한다.
6. 기존 원본과 신규 저장소의 판수·시즌별 판수·개인 승수·번복 결과를 대조한 뒤 전환한다. 백업과 복구 절차도 함께 검증한다.

과거 데이터 복구 배경은 [PARSE_REPORT.md](../../../docs/PARSE_REPORT.md)에 있다. 실데이터 마이그레이션과 신규 UI를 한 번에 전환하지 않는다.

### 11-1. 개발 앱 준비

3. OAuth2 Client ID와 Secret을 설정한다. 기존 설계의 Redirects 자리표시자는 `https://127.0.0.1`이다. 포털과 SDK 흐름에서 요구하는 값을 실제 인증으로 검증한다.
4. `bot`, `applications.commands`로 TEST2에 초대한다. View Channels, Send Messages, Embed Links, Read Message History 등 필요한 채널 권한을 확인한다.
5. Activities를 활성화하고 Web·iOS·Android를 지원 대상으로 설정한다. 개발자 이외 테스트 계정의 접근 권한도 확인한다.
6. TEST2의 명령 채널과 TEAM1·TEAM2를 `config.json`에 맞춘다. 일부 채널 누락을 전체 정상으로 취급하지 않는다.
7. 기본 Entry Point 명령과 `bot.sync_commands()`의 공존을 검증한다. 동기화 때문에 실행 명령이 삭제되지 않아야 한다.

### 11-2. URL Mapping

긴 prefix를 앞에 두고 `/`를 마지막에 둔다. target에는 프로토콜과 `index.html`을 넣지 않는다.

| prefix | 운영 target | 개발 target |
|---|---|---|
| `/pick-api` | `pick.hansoljj.com/pick-api` | 별도 매핑 없이 아래 Vite 프록시 이용 |
| `/ddragon` | `ddragon.leagueoflegends.com` | 동일 |
| `/` | `arena.hansoljj.com/pick` | quick tunnel 호스트명 |

### 11-3. 개발 세션

- 봇은 `uv run python -u got_champe.py`, Vite는 해당 웹 소스 폴더에서 `npm run dev`로 실행한다.
- Vite의 `/pick-api`를 `http://127.0.0.1:8790`으로 프록시하고 `ws: true`를 설정한다.
- `cloudflared tunnel --url http://localhost:5173`으로 받은 호스트를 dev 앱 `/` 매핑에 넣는다. 종료 후 임시 호스트 매핑을 정리한다.
- Vite allowedHosts에는 실제 터널 호스트를 허용한다. 기존안 `.trycloudflare.com` 전체 허용보다 실제 주소를 우선한다. HMR `clientPort: 443`을 출발점으로 프록시 경로를 검증한다.
- Vite·SDK·윈도우 cloudflared는 설치 필요 여부를 먼저 확인하고, 새 패키지 설치는 사용자 규칙에 따라 승인 후 실행한다.
- 단일 테스트 계정으로 가상 6명을 조작하는 테스트와, 서로 다른 실제 계정의 권한·동시성 테스트를 구분한다.

추가 환경변수는 `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, `ACTIVITY_PORT`(기본 8790)이다. 기존 `DISCORD_TOKEN`, `DEV_MODE`, `ARENA_GH_*`도 단계에 맞춰 유지한다.
프론트에는 공개 `VITE_DISCORD_CLIENT_ID`만 넣고 secret을 넣지 않는다. `.env.example`에는 값 없이 필요한 키를 기록한다.

## 12. 맥미니 운영과 전환

### 12-1. pm2 자동 기동

기존 조사상 pm2는 launchd의 `pm2.hansol.plist`로 실행되고 자동 로그인 `hansol`에 의존한다. 봇 경로는 `~/projects/lol_discord_bot`, uv는 `/opt/homebrew/bin/uv`였다. 실행 전에 현재 상태를 다시 확인한다.

```js
module.exports = {
  apps: [{
    name: 'lol',
    script: 'uv',
    args: 'run python -u got_champe.py',
    interpreter: 'none',
    cwd: __dirname,
    autorestart: true,
    restart_delay: 5000,
    max_restarts: 20,
    kill_timeout: 5000,
    time: true,
  }],
};
```

`ecosystem.config.cjs`로 저장한다. PATH에 uv가 없으면 확인된 절대경로를 사용한다. `.env`는 봇 cwd에서 읽고 pm2 설정에 secret을 복사하지 않는다.
중복 봇 프로세스가 없는지 확인한 뒤 `pm2 start ecosystem.config.cjs`, `pm2 save`를 각각 실행한다.
`pm2 restart lol`, 종료 정리, 재부팅 후 lol·finance 복귀를 검증한다. 로그는 `pm2 logs lol`과 기존 `logs/`를 사용한다.

### 12-2. 터널과 운영 공개

`~/.cloudflared/config.yml`의 마지막 404 규칙 앞에 다음 ingress를 추가한다.

```yaml
- hostname: pick.hansoljj.com
  service: http://127.0.0.1:8790
```

DNS는 `cloudflared tunnel route dns finance pick.hansoljj.com`으로 연결한다. 기존 운영 절차의 `launchctl kickstart -k gui/$(id -u)/com.cloudflare.cloudflared`는 맥미니에서 실행하는 명령이다.
터널 재시작은 finance도 잠시 끊으므로 작업 시각을 사용자와 맞춘다. 이 작업에서 cloudflared 업그레이드까지 묶지 않는다.
운영 앱 Activities·플랫폼·URL Mapping·OAuth를 확인하고 `.env`를 설정한 뒤 유휴 상태에서 `pick_ui: activity`로 전환한다.
실전 한 판의 카운트다운·픽·자동 배정·기존 승리 처리·대시보드 반영을 확인한다. 실패하면 판을 정리한 후 embed 모드와 이전 웹 빌드로 되돌린다.

## 13. 구현 순서와 완료 조건

각 단위는 검증 후 커밋한다. 자동 push는 하지 않는다. 구현 체크박스는 실행 증거가 있을 때만 완료 처리한다.

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 0 | 현황 확인·pm2 자동 기동 | 운영 프로세스 중복 없음, restart·재부팅 후 복귀 |
| 1 | dev 앱·token/ws/ping·카운트다운 측정 골격 | PC·모바일 각 100회 RTT 기록, p95 < 1초. 넘으면 서버 경로·유예 재검토 |
| 2 | 저장소·웹 배포 구조 확정 및 통합 | 사용자 작업·Git 이력 보존, 웹 출력만 배포, 기존 전적과 봇 경로 정상 |
| 3 | 공통 픽 처리 추출 | 기존 embed 모드 한 판과 저장소 내 회귀 테스트 통과 |
| 4 | 서버 시간·상태·권한·WS 프로토콜 구현 | 이전 게임/턴·중복·후보 밖 입력 거절, 마감 경합에서 1회 확정 |
| 5 | 액티비티 UI·연결 복구 | 양쪽 팀 실제 계정에서 같은 판 확인, 14절 카운트다운 기준 통과 |
| 6 | 1차 운영 전환 | 실전 한 판과 기존 결과·전적 반영 확인, 되돌릴 수 있는 전환 상태 유지 |
| 7 | 결과·전적 공통 처리와 화면 연결 | 저장 정책 확정, 중복·실패 복구·기존 전적 대조·열린 화면 갱신 검증 |
| 8 | 안정화 후 기존 경로 정리 | 사용자와 정리 시점 결정, 구 카운트다운·임시 배포 제거, 운영 문서 갱신 |

단계 2가 지연돼도 단계 1의 측정과 단계 3의 봇 회귀 검증은 독립적으로 진행할 수 있다. 저장소 통합이 카운트다운 개선 가능성 측정을 막지 않게 한다.

## 14. 검증·관측 기준

### 카운트다운 최우선 검증

- 정상 전경·무입력·연결 유지 상태에서 양쪽 팀의 20초 카운트다운이 멈추지 않고 실제 마감에 따라 감소한다. 이른 정상 선택 시 즉시 다음 턴으로 넘어가는 것은 정상이다.
- 시스템 시계가 ±40초 틀린 테스트 환경과 실행 중 시계 변경을 시뮬레이션해 표시가 로컬 벽시계에 끌려가지 않는지 확인한다. 호스트 시스템 설정을 임의로 변경하지 않는다.
- 새 참가·재접속은 현재 남은 시간부터 표시한다. 연결 중·끊김·마감 확인 상태가 빈 화면과 구분된다.
- 한 연결 지연·차단, 한 채널 embed 실패, 메시지 삭제가 다른 참가자의 액티비티 카운트다운을 막지 않는다.
- 모바일 백그라운드 후 전경 복귀, 절전 복귀, 연결 복구 때 최신 턴과 시각을 다시 받는다. 오래된 턴의 입력을 보내지 않는다.
- 마지막 순간 클릭·중복 클릭·자동 배정 동시 실행에서 한 명의 선택과 턴 이동이 각각 한 번만 기록된다.

### 테스트와 로그

- Python 규칙 테스트는 저장소 `tests/`에 보존한다. 기존 `e:\tmp`의 exec 테스트는 참고 자료이며 유일한 검증 근거로 쓰지 않는다.
- 서버 판정, 요청 멱등성, 권한, 잘못된 JSON·후보·턴, 느린 연결, 스냅샷 역순, 세션 만료·서버 재시작을 검증한다.
- 프론트 빌드와 실제 Discord PC·모바일 실행을 모두 확인한다. 한 계정 DEV_MODE 통과만으로 실제 6명 동작을 완료 처리하지 않는다.
- game/turn/request ID, phase/version, 서버 접수·확정 시각, RTT p50/p95/최대, 자동 배정 사유, 연결 종료 사유와 채널 편집 오류를 기록한다. 비밀과 세션 토큰은 남기지 않는다.
- 상태 전달 지연도 측정한다. ping RTT만으로 픽 반영·초기 화면 표시가 정상이라고 결론내리지 않는다.

## 15. 단계별로 남은 결정
